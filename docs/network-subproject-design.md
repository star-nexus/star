# star-network：自托管网络接入子项目技术设计

状态：首版已在独立仓库实现；尚未宣称完成公网或 ChatGPT 验收。暂名 `star-network`，与 [StarBench 主设计](self-hosted-mcp-design.md) 配套。它是可独立发行的部署基础设施，不是新增游戏层或另一套 MCP 业务服务。

## 1. 职责与交付边界

将运营者拥有的 HTTP/WebSocket 服务，以可验证的公网 HTTPS/WSS 地址发布。统一处理 DNS/TLS、入口配置、可选隧道、故障状态和恢复，隔离底层网络环境差异。

需要交付独立源码仓库/包、版本化 CLI/配置契约、通用服务测试、平台适配器和运维文档。StarBench 部署包固定其版本与校验值；无需把子项目源码放进 `framework`、`rotk_env` 或 `starbench_arena`。首版通过进程调用和 JSON 文件交互，不要求业务应用导入某种语言的 SDK。

它可以读取网络计划并启动网络组件，但不能启动游戏、认领 Units、修改赛事数据库、解析或执行工具业务参数。StarBench 核心的开发和本机运行不能依赖该子项目已安装。

子项目不接管应用协议实现：MCP 工具注册、OAuth 令牌验证、star-protocol SDK 与 HUB 路由仍在原有模块中。它也不是一个暴露给模型调用的网络配置工具。

## 2. 内部分层

| 层 | 职责 |
|---|---|
| 契约/规划 | 校验通用服务描述、公开地址和入口约束，生成可审查部署计划 |
| 入口适配器 | direct、self-hosted relay、existing ingress 的配置和状态采集 |
| 基础设施驱动 | 首版 Caddy/OpenSSH、可选 DNS/证书接口；隔离具体软件和供应商差异 |
| 平台驱动 | macOS 进程/服务管理、Linux 服务管理、容器网络和生命周期 |
| 诊断/观测 | 分层检查、证据、可执行修复建议、脱敏日志 |

适配器使用能力声明而非在业务应用中增加大量条件判断。能力至少包括 HTTP streaming、WebSocket、TLS、DNS 更新和公网检查支持。输入要求超过能力时直接报错，不静默降级为另一种连接或商业服务。

## 3. 支持的入口方式

### direct

公开入口与目标应用在同一主机或运营者可控制的私网中。首版由 Caddy 提供 HTTPS；主机直接可达，或路由器将流量转入主机。子项目给出端口、路由和防火墙需求，但不默认自动修改路由器或启用 UPnP。

### self-hosted relay

公开入口在运营者控制的另一台机器，目标主机主动建立加密连接。首版使用 OpenSSH 反向端口转发和守护机制。代理到 relay 的回环转发端口；不把该转发端口额外公开。组件跨容器网络时通过部署适配器提供仅代理可达的私有地址，不能硬编码错误的 localhost。

SSH 主机指纹必须验证，转发目标及监听范围固定，凭据专用。隧道恢复使用有上限的退避与抖动，不能忙循环或重复打印完整业务载荷。

它是可选适配器，不要求有直接公网入口的主机再购买一台 VPS，也不要求社区服使用 StarBench 官方 relay。

### existing ingress

运营者已有反向代理、负载均衡器或其他自管入口。子项目导出要求并执行检查，默认不覆盖已有配置。必须说明哪些组件由外部管理员维护。此模式让 StarBench 无需绑定 Caddy 或 OpenSSH。

## 4. 网络场景与判定

| 条件 | 计划 | 不得做出的推断 |
|---|---|---|
| VPS 公网地址和允许的入站端口 | direct 或 existing | 本机端口监听成功不代表安全组/外网路径已放通 |
| 家庭公网 IPv4、可转发 | direct；稳定 LAN 地址，公网变化时可选 DDNS | 路由器显示 WAN 地址不必然表示它是可外部访问的公网地址 |
| 双重 NAT | 确认并配置每层映射，或自有 relay | 只配置内层路由器就认为可达 |
| IPv6 / 双栈 | 独立检查 AAAA、路由、防火墙及目标客户端路径 | 有 IPv6 地址就代表 ChatGPT 或其他客户端能连接 |
| CGNAT、无允许入站 | 自有 relay；没有该资源则待配置 | 应用能自动创造公网地址或穿过任何 NAT |
| 443 入站被阻断 | 查清网络策略或选择自有入口；其他公开端口仅在目标客户端实测支持时采用 | DNS-01 证书签发成功就解决了入站阻断 |
| 动态公网地址 | DNS 适配器更新记录并记录检测时间/TTL | DNS 切换即时生效，或活动连接自动无损迁移 |
| 本地能用域名、外网不能用 | 从独立外部路径复测；检查分流 DNS、回流 NAT | 家庭局域网 curl 成功等于公网验收成功 |
| 主机休眠、切换网络或隧道掉线 | 报告 unavailable，恢复网络组件 | 远端仍可用，或自动暂停比赛/重放请求 |

不自动发布未经验证的 AAAA。没有外部探测者时，将公网验证标为 unknown，保留原因。外部证据可由运营者的另一台主机、独立网络或目标客户端提供，不强制使用某个第三方探测平台。

## 5. 版本化接口契约

首版契约为 schema_version 1；独立仓库提供 schema/deployment-v1.schema.json、Python 校验和 JSON CLI。

### 输入：DeploymentSpec

- `schema_version`、`deployment_id`：契约版本和实例标识。
- `services[]`：通用服务 ID、公开 host、内部 upstream、路由匹配、HTTP streaming/WebSocket 要求、可选只读健康检查路径。网络层不理解这些服务是不是游戏或认证服务。
- `ingress`：适配器名和私有适配器配置。路由器、relay、网络接口等信息只属于此部分。
- `tls`：证书来源/签发策略和续期设置。
- `dns`：静态/动态维护策略及可选驱动。
- `secrets`：受保护文件或操作系统凭据存储的引用；普通计划/状态输出不内嵌 secret 值。
- `checks`：期望验证范围、外部探测来源和证据有效期。

upstream 与公网 host 由管理员控制，不能从普通客户端请求中动态指定；禁止把运行入口做成任意目标的开放代理。

### 输出：Plan / EndpointSet / StatusReport

- Plan：待变更组件、端口、文件、DNS/证书动作、版本，以及哪些操作需管理员手动完成。先生成、再应用。
- EndpointSet：各服务的规范外部 URL、内部目标标识、公开监听范围和已应用配置版本。不包含 SSH/DNS/token 等凭据，也不替应用生成 OAuth audience 或用户授权。
- StatusReport：组件状态、检查项、故障分类、时间戳和观测来源；提供“尚未验证”状态。

StarBench 部署层读取 EndpointSet 后配置 Arena 的公开 URL 和 Keycloak 的 issuer/回调。它必须验证输出属于当前部署，域名与预期一致；不能信任未经校验的网络进程输出去更改身份资源。

### 生命周期操作

语义操作为 `validate → plan → apply → status`，另有 `diagnose`、`stop` 和受控回滚。首版 CLI 已采用这些命令名，详情见独立项目 README。

- 同一配置重复 apply 应幂等，不创建重复隧道/服务；同实例并发 apply 必须互斥。
- 配置写入尽量原子；应用失败保留最后已知配置和诊断，不部分覆盖后声称成功。
- stop 仅停止该实例拥有的网络进程，不杀占用同端口的其他程序，不停止 ENV 或数据库。
- 重启网络组件不承诺无连接中断；现有 SSE/WSS 客户端按其协议重连。
- 兼容版本采用显式 schema 版本检查；不支持的主版本拒绝，不能靠猜测解析。

## 6. 数据面要求

网络入口属于透明传输层。对 StarBench 使用场景，适配器必须满足：

1. 保留 MCP 请求方法、必要协议头、Authorization、Content-Type、状态码和认证挑战；支持 POST 以及协商使用的 GET/SSE，不缓存认证后的观测与工具结果。
2. 支持流式响应，不把 SSE 缓冲为完整正文后才发送；长连接/空闲时限显式配置并测试。
3. 支持原生协议所需 WebSocket Upgrade，不混淆 HTTP 与 WS 健康状态。
4. 不自动重试或重放请求体，不添加业务队列、去重或批量优化；传输恢复不等于动作重试许可。
5. 未知业务状态返回连接失败/网关错误，不能伪造工具成功或把错误包装成正常观测。
6. 不记录完整请求体、Authorization、cookie 或团队消息。连接日志使用脱敏元数据和通用关联 ID。
7. 对 Host/转发头建立明确规则。只信任配置的代理链，过滤客户端伪造的转发头；不能通过错误 scheme/host 生成 localhost OAuth URL。
8. 公网服务清单显式列出，仅将 MCP/受保护原生入口、观战/榜单和必要认证路由公开。控制与诊断接口默认私有，端口不得无差别透传。

TLS 可在运营者管理的入口终止；跨公网到后端必须经过受认证的加密路径。同机回环/受控私网的边界由部署适配器声明，不能默认把“内网”视为任意可被信任的来源。

## 7. 诊断与健康模型

不同维度独立报告，不压缩为一个含义模糊的 online 标志：

| 检查 | 能证明什么 |
|---|---|
| 配置有效 | schema、目标、端口和引用合法 |
| 组件存活 | 代理/隧道进程运行 |
| upstream 可达 | 从实际代理所在网络命名空间能连接目标 |
| DNS 正确 | 指定解析路径上的 A/AAAA 与计划匹配 |
| TLS 有效 | 主机名、链和有效期通过验证 |
| 外部入口可达 | 某个独立外网探测者在指定时间能够访问公开地址 |
| 客户端业务验收 | 由 StarBench/客户端记录 OAuth、MCP 和游戏工具执行证据，不由网络子项目判定 |

每项记录 `pass / fail / unknown`、观测时间、来源和有效期。之前成功但已过期不能当作当前正常。内部 DNS 查询、本机公网回环访问与真正外部探测必须使用不同来源标记。

故障分类至少包括配置错误、端口冲突、DNS 不符、TLS 失败、upstream 不可达、隧道中断、外网未验证。诊断可以给出建议，不自动改路由器、重置防火墙或切到托管中转来“修好”。

## 8. 依赖与许可证原则

首版选成熟软件而非手写代理或 NAT 穿透算法：Caddy 是默认 HTTPS 驱动，OpenSSH 是可选 relay 驱动；它们不是核心业务依赖。DNS 驱动按接口扩展，不绑定一家云厂商。

Desktop Commander 的源码可用于理解就绪检查、凭据更新、退避等行为，实际复制时遵守主设计中的来源和许可证记录要求。不复制其默认商业端点、遥测上传或 Supabase 后台耦合来充当 StarBench 的网络实现。

发行应固定组件版本与可验证来源，保留必要许可。核心业务无需跟随某个网络软件版本升级；适配器兼容性通过该子项目的测试确认。

## 9. 首版实施边界与验收

首版顺序：通用契约与假实现 → direct/Caddy + existing → macOS/Linux 部署驱动 → 外部证据报告 → 可选 SSH relay/DDNS。路由器自动配置、任意 NAT P2P 打洞、多地域流量调度和自建通用设备云不在首版范围。

必须覆盖：

- 用通用回显 HTTP/SSE/WS 服务验证子项目，不依赖 Rust 或 StarBench 数据库。
- direct 与 existing 入口可替换；切换实现不修改 StarBench 核心代码或工具 schema。
- 端口占用时准确报告冲突，不停止未知进程；权限不足时给出缺失条件。
- SSE/WSS 长连接、空闲、断线与恢复；确认代理不自动重发有副作用请求。
- A/AAAA 不一致、动态 IP、证书续期失败、relay 断线和主机休眠；不误报可达。
- OAuth 发现/登录/回调通过公开地址由上层联合验证；未配置外部探测时状态保持 unknown。
- 升级失败可回退网络配置，不触碰比赛状态；停止子项目只影响它拥有的组件。
- 不含第三方托管中转的默认依赖；无网络子项目时 Arena 本机测试仍可运行。

网络层保证的是明确配置下的传输能力和可观测状态，不保证上层模型一定行动、游戏公平性、比赛不中断或任何硬件容量。

## 10. 当前研发实例覆盖规则（2026-10-15）

当前 Mac 的 STAR 配置使用 existing；不对 mcp.starverse.chat 重复发起 ACME、不读取独立 Mac MCP Gateway 的证书目录、不修改其启动配置，也不启动公网 Caddy。独立主机的 direct/DNS-01 和外部证书文件模式继续保留。

existing 不读取 DNS 凭据，不启动或重载外部代理。它只给出路由要求和检查结果；运营者实际添加路由是单独的集成步骤。网络健康报告不能替代 OAuth 和模型客户端验收。


## 2026-11-04：可选客户端 Tunnel 适配器

在运营者明确选择下，0.1.1 提供独立 `star_network.tunnel` 进程适配器，可与 direct/existing 并用。它使用运营者提供的官方 tunnel-client、Tunnel ID 和私密运行凭据；不创建远程 Tunnel，不改其他项目配置，不安装应用 Authorization 头。管理接口只监听回环，停止操作校验 PID 身份。原 v1 HTTPS 契约保持兼容，无需 Tunnel 的用户不增加安装步骤。

适配器不将进程就绪标为客户端工具调用通过。不同应用应使用不同 Tunnel ID；临时重定向必须先停止旧转发并保存恢复配置。应用仍负责 OAuth 和用户权限，网络组件不签发游戏令牌。
